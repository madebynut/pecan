# Word 原生边框与单元格留白

## 未发布（0.8.13 之后）表格单元格的列表与任务项在 PDF、HTML 中还原（2026-11-10）

现象：`| 任务列表 | - [x] **已完成**<br>- [ ] 待办 |` 导出 Word 是两个带复选框的列表项，导出 PDF 是两行文字 `- [x] 已完成`、`- [ ] 待办`，导出 HTML 是带圆点的 `[x] 已完成`、`[ ] 待办`。

根因：三种格式各有一条单元格路径。Word 读取 `table::events`，它把含 `<br>`、`<ul>`、`<ol>` 或以列表标记开头的单元格改写成块级 Markdown 重新解析，得到段落、列表、任务标记等事件。HTML 使用原始解析结果，输出净化之后再用正则 `table_lists` 补列表：只认每一行都是同一种列表项的单元格，不认任务标记、单个项目、说明与列表混排，有序列表丢失起始编号。PDF 也使用原始解析结果，并且单元格的数据结构是一行文字，列表标记、`[x]` 和 HTML 列表标签都只能当作文字或被丢弃（`<ul><li>父项<ul><li>子项…` 输出为「父项子项同级项」）。任务项只是这条分叉里最显眼的一个症状。

修复：HTML 与 PDF 改为读取同一事件流。

- HTML：解析入口换成 `table::events`，删除 `table_lists`。复选框、有序列表起始编号、嵌套列表由正文同一套输出生成。样式表为单元格内的段落和列表增加紧凑间距，并让圆点层级从单元格起算。
- PDF：单元格由 `Vec<Inline>` 改为 `Vec<Para>`，与正文段落同一结构，带标记和相对单元格的缩进。构建器用 `Table.outer` 记录表格外层容器数，单元格内的缩进、标记和列表层级只看单元格内部；提示块的图标和标题不会进入单元格。排版把每个单元格的段落逐段断行，列表项间距 0.2 字高、段落间距 0.5 字高，续页的部分从单元格内边距开始。
- Word 未改。

各格式结果（`samples/word-table-lists.md` 与探针文档，PDF 用 PDFKit 光栅化、HTML 用 Chrome 无头截图逐行目视）：任务项为圆点加复选框，与正文任务列表一致；有序列表从 3 起；单个项目带圆点；说明、列表、结尾各自成段；HTML 嵌套列表为圆点、空心圆两级；代码内的 `<br>` 保持原样；折行的列表项悬挂对齐；引用和列表内的表格相同。真实技术方案第 2 页「服务职责」表由带星号的文字变为列表。

版式变化：

- PDF 中含 `<br><br>` 的单元格，原先是一个空行，现在是段落间距，行高变矮。
- HTML 中含 `<br>` 的单元格内容包在 `<p>` 里，外观不变；列表单元格去掉了浏览器默认的上下 1em 外边距。HTML 列表（`<ul><li>`）的每一项内部带 `<p>`，间距与紧凑列表相同。
- 居中或右对齐列里的列表项，PDF 与 Word 一样连同标记逐行对齐。

回归：PDF 构建器两项测试先写，在旧实现上失败（任务、有序、单项、混排、嵌套、缩进代码、分隔线各一行；提示块以表格开头时图标不进入单元格）。HTML 一项替换原 `table_lists` 测试，旧实现失败。PDF 排版新增两项：标记与首行同基线且悬挂缩进、列表项间距小于段落间距；跨页的 80 项单元格不丢项不重复，续页从内边距开始。22 份样例和一份真实技术方案用修改前后两版导出四种格式：Word 23 份逐字节相同；Markdown 除随机资源目录名外相同；PDF 19 份逐字节相同，其余 4 份共 6 页不同：5 页含列表单元格，1 页是表格变矮后一个提示块前移到上一页；HTML 去掉样式表后 16 份逐字节相同，其余 7 份的差异全部位于表格单元格内。266 项工作区测试通过，11 项环境专项 ignored；rustfmt、严格 Clippy、warnings-as-errors rustdoc 通过。

HTML 任务项的复选框与列表圆点对齐到同一行中线。原生复选框默认贴在字母基线上，方框会高出居中的圆点；样式改为 `vertical-align: middle`，并去掉浏览器自带的上下外边距。Chrome 3 倍图里圆点、复选框和文字在同一水平线上。

未验证：HTML 只看了 Chrome，没有看 Safari、Firefox 和打印输出；PDF 只用 PDFKit 查看。未重新打包应用，版本号未变。

## 未发布（0.8.13 之后）HTML 表格列对齐（2026-11-10）

现象：`:---`、`:---:`、`---:` 在 PDF 和 Word 中生效，HTML 里每一列都靠左。

根因：pulldown-cmark 把列对齐写成单元格的 `style="text-align: left|center|right"`。净化器删除全部 `style`，而白名单里的 `align` 属性从未被写出来。

修复：净化之前，只把单元格上这一条完整的对齐声明改成 `align`。带有其他声明的 `style` 原样留给净化器删除，文档里的任意样式仍然进不去。样式表让单元格里的列表缩成内容宽度后按列放置，否则只会移动文字、把圆点留在左边。段落沿用已有的 `text-align: inherit`。

Chrome 无头截图：左、中、右三列的表头、文字、段落和列表都落在各自的一侧或中间；右对齐列的有序列表整块靠右，序号仍在文字左侧。未写对齐的表头仍按浏览器默认居中，正文靠左，与修改前相同。

回归：一项测试先在旧实现上失败，覆盖三种对齐、列表单元格，以及带额外声明的 `style` 和写在 `div` 上的同样声明都被删除。样例和技术方案的源文件都没有列对齐标记。21 份未改动的样例，HTML 正文、Word、PDF、Markdown 与上一版逐字节相同，HTML 只有样式表不同。

未验证：Safari、Firefox 和打印。未重新打包应用，版本号未变。

## 未发布（0.8.13 之后）行内代码胶囊改为单一灰底（2026-11-10）

现象：表格中的胶囊，灰底高出自己的上边框。Microsoft Word 原生画面里，`word-inline-borders.md` 在 100% 下表格内每个胶囊的灰底都比上边框高 1px；200% 下英文胶囊高 2px，同一行的中文胶囊齐平。正文段落里 200% 下英文胶囊高 3px。与公式同行时最明显：200% 下灰底比边框上方多 3—6px、下方多 9px。

根因：Word 用两套几何绘制同一个胶囊。字符底纹（`w:shd`）铺满整行的行框，行框由该行最高的文字决定；字符边框（`w:bdr`）只围住带边框的那几个 run 自己的字体框。代码字体 Menlo 10pt 的字体框是 12pt，同行中文 Hiragino Sans GB 10pt 是 13pt，于是灰底比边框高出 1pt。只有胶囊恰好是该行最高的文字时两者才重合，所以单独成行的胶囊、纯英文行里的胶囊、中文胶囊看起来正常。

这不是 0.8.9 新引入的缺陷，而是被它暴露的：0.8.7／0.8.8 的 1pt 边框距离碰巧把边框推到中文行框附近，代价是两侧白条；0.8.9 把距离改回 0 消除白条，上下的错位就显现出来。此前各版在「上下边消失」「两侧白条」「灰底越界」之间来回，都是同一个原因。

排除的方案（均在原生 Word 中实测）：

- 边框距离 1pt：上下碰巧齐平，两侧恢复白条，且只对 10pt 中文行成立。
- 代码 run 显式指定东亚字体、左右留白改用正文中文字体：无变化或仍差 1px。
- 在胶囊内放一个与段落同字体同字号、宽度 1% 的全角空格撑高边框：上边齐平，下边与灰底之间出现白缝；纯英文行上下都出现白缝；胶囊单独成行时无效。

这些方案都只是让两套几何在某一种字体组合下重合。

修复：胶囊只用底纹一种方式绘制，删除字符边框（`INLINE_CODE_SHADING`）。没有第二套几何，灰底不可能越界，「上下边被裁掉」这一类问题也一并消失。没有描边后 F2F2F2 在表头 F5F5F5 和引用 F7F7F7 上几乎看不见，灰底改为 E8E8E8；在白底、表头、引用和四种提示块底色上对比过 F2、EC、EA、E8、E5 五档后选定。左右留白 run、斜体间隔、表格行高与单元格留白、字号均未改。HTML 与 PDF 的胶囊仍是灰底加细边框，浏览器和 PDF 排版中两者几何一致，不受影响。

原生核验（Microsoft Word for Mac，非 Retina 捕获）：逐个胶囊检查灰底是否为完整矩形、四周有无旧边框或旧底色残留。

- `word-inline-borders.md`：75、90、100、110、125、150、175、200、250、300、400% 共 11 档，画面内 5—30 个胶囊全部为完整矩形。50% 时胶囊不足 8px，未做自动判定，目视正常。
- 混排探针（标题、正文、斜体相邻、行内公式、表头、表格、提示块、引用、列表）：75、100、125、150、200、300% 共 6 档，15—27 个胶囊全部为完整矩形。
- 真实技术方案首页：75、100、125、200%，3—4 个胶囊全部为完整矩形。

版式变化：胶囊没有边框；灰底高度等于所在行的行框，因此同一行内所有胶囊上下齐平，不同行之间随该行文字而变（200% 下纯英文表格行 24px、含中文的表格行 26px、正文行 29px、含分式的行 38—41px）。相邻的两个胶囊之间若没有任何字符，灰底会连成一块。

回归：四项测试在旧实现上失败（其中一项为新增，导出整份样例并断言文档和样式中不存在字符边框）。22 份样例和一份真实技术方案用修改前后两版各导出四种格式：HTML、PDF 全部逐字节相同；Markdown 除带图文档的随机资源目录名外相同；Word 23 份都只有胶囊装饰这一处差异，共 1018 处，其余 XML 逐字节相同。262 项工作区测试通过，11 项环境专项 ignored；rustfmt、严格 Clippy、warnings-as-errors rustdoc 通过。

未验证：Windows 版 Word、Retina 屏幕、打印输出、WPS、LibreOffice（本机没有）。Word 也认可只写在字符样式里的底纹（两种写法 100% 和 200% 逐像素相同），每个 run 上的直接格式是为其他阅读器保留的，这一点没有实测。未重新打包应用，版本号未变。

## 未发布（0.8.13 之后）嵌套表格底边的根因修复（2026-11-10）

复核结论：0.8.9—0.8.13 对提示块内代码使用的 `tblCellSpacing=1` 分离模式加 0.75pt 外框，遮住了症状，没有消除原因。下方 0.8.5—0.8.11 各节对底边丢失的解释（合并边框在部分缩放下丢线）以本节为准。

根因：单元格以嵌套表格结尾时，Word 要求其后有一个段落；这个段落为空时 Word 不给它高度，嵌套表格的底边落在这段位置上，被带底色和边框的外层单元格盖住，是否可见取决于缩放。任何以嵌套表格结尾的单元格都受影响，不只是代码。

旧实现在 Microsoft Word 原生画面（同一文档、同一窗口）的表现：

- 40%—90%：提示块内三张代码卡片的语言栏分隔线都不可见；结尾在提示块末尾的两张卡片，底边在 40%、50%、60% 不可见，75% 和 90% 各缺一张。60%、75%、90% 语言栏下出现白缝。
- 100%—175%：表格外框与单元格外框各画一次，顶边 2px、分隔线多为 2px；结尾在提示块末尾的卡片底边只有 1px（仍被盖住一条），其后还有正文的卡片底边为 2px。
- 提示块以数据表格或嵌套提示块结尾时，底边在部分缩放下丢失，这两种情况旧实现没有处理。

修复：每个单元格在嵌套表格之后的最后一段写入一个不换行空格，行高 3pt（`CELL_END`）。1pt 和 2pt 在 50% 以下会被舍入掉。代码卡片随后在所有容器中统一使用合并模式的 0.5pt 外框和分隔线（`CODE_BORDERS`），删除 `tblCellSpacing`、0.75pt 外框和按容器切换的分支。数据表格单元格、引用、提示块共用同一处理（`Docx::cell_final`）。

原生核验（Microsoft Word for Mac，非 Retina 捕获，约 1px/pt）：

- 四种代码卡片（`:::` 末尾、`:::` 中间、提示块末尾、引用末尾）在 40、50、60、75、90、100、105、110、115、120、125、150、175、200% 共 14 档，五条边均为 1px 且全部存在。33% 时底边存在，部分左边细线不可见。
- 提示块以数据表格、嵌套提示块、引用、代码结尾：50%、75%、100% 底边完整。
- 表格内行内代码胶囊：当时目视判定 75%、100%、125% 四边完整，这一判定有误：边框完整，但灰底高出上边框 1px，见上一节。

版式变化：提示块内代码之后还有正文时，间距由 7pt 变为 5pt，与正文中的代码一致；以嵌套表格结尾的单元格底部多出 3pt（提示块为 9pt 内边距加 3pt）。

已知残留：部分缩放下，嵌套表格底边正下方有 1px 白线横贯外层单元格，出现与否取决于缩放和表格在页面上的位置。代码探针文档上 0.8.13 出现在 60%、110%、125%，本次出现在 60%、105%、110%、125%、150%，每档各一张卡片；75%、90%、100% 两版都没有。提示块中间的数据表格（本次未改的路径）在 75% 也有一处。给后续段落或外层表格加底色都不能消除，未继续处理。

回归：新增或改写的三项测试在旧实现上全部失败。22 份样例和一份真实技术方案用新旧两版各导出四种格式：HTML、PDF 全部逐字节相同；Markdown 除两份带图样例的随机资源目录名外相同；Word 有 10 份逐字节相同（含技术方案），其余 13 份只有代码卡片边框属性和单元格末段两类差异。261 项工作区测试通过，11 项环境专项 ignored；rustfmt、严格 Clippy、warnings-as-errors rustdoc 通过。

未验证：Windows 版 Word、Retina 屏幕、打印输出、LibreOffice（本机没有）。未重新打包应用，版本号未变。

0.8.9 仅修订 Word 导出布局。上一版用户验收发现胶囊两侧有白条、部分上下边缺失，周围斜体还会触碰边框。最终方案保留可编辑文字和原生表格，没有栅格化文本或增加绘制线条。

### 胶囊与单元格

Word 不会为字符边框的 `w:space` 区域绘制字符底纹。胶囊统一使用灰底 F2F2F2、0.5pt 浅灰字符边框和零边框距离；已有着色的窄 NBSP 提供左右内边距。字符样式与每个 run 共用同一装饰常量，灰底一直覆盖到边框，移除两侧白条。

所有数据表格仍共用 `TableCell` 的 1.15 倍自动行距、零段前段后留白与原生 `vAlign=center`。上下单元格留白由 4.5pt 增为 6pt，行高设置为 24pt 的原生最小值，长文本、列表和显式换行可以自然增高。没有胶囊专用的段落样式、固定行高、外部空段落或额外行距。

斜体字形可能伸出正常字宽。仅当无空格的斜体紧邻胶囊时增加窄的不着色间隔；普通文字、已有空格及胶囊内部格式不增加外间隔。Markdown 与 HTML code 共用开始／结束入口，段落、换行与图片重置相邻状态。处理按 run 顺序进行，不增加全文扫描、字体测量或依赖。

### 代码卡片

代码继续采用同一原生两行表格：0.75pt 外框、0.5pt 分隔线、24pt 可增高的语言栏，以及跨页重复语言栏。1 twip（0.05pt）的非零原生表格间距选择 Word 的分离边框绘制模式，避免合并网格覆盖细边框；不会形成此前 1pt 间距的可见白色接缝。不叠加单元格边框，不加粗外框。

保留完整可编辑代码、语法高亮、格式化结果、内部留白和必要的末尾小字号段落。提示图标继续采用用户选择的 A 方案：根据首行可见字形中心，只调整原生行内图标的基线，不移动文字。
